# Knowing your hardware

If I go to Apple's official site and check the specs for my macbook air M1, I get the following details - 
> Apple M1 chip 
>
> 8-core CPU with 4 perform­ance cores and 4 efficiency cores
>
> Memory: 8GB

I remember my Comp Architecture Prof. telling us that it is embarassing to be a Computer Science graduate and not understand the hardware specs of your own laptop. In an effort to not let her down, let's try to understand what these 'cores' mean.


**Definition:** cores are the individual processing units within a motherboard. 

Wikipedia mentions that the four high-performance "Firestorm" cores run at up to 3.2 GHz. Whereas the four power-efficient "Icestorm" cores run at lower speeds around 2.06 GHz. 

```zsh
> sysctl hw.logicalcpu hw.physicalcpu
hw.physicalcpu: 8 # number of cores
hw.logicalcpu: 8 # number of "hardware threads" => 1 per 1 core
```

Number of logical cpus is the number of different actualy "threads of instructions" you can execute parallely. Some chips have 2 hw threads per core.
Each core has its own L1/L2 cache usually. The L3 cache might be shared across all cores which is connected to the RAM memory.

## A simple example

```c++
#include <iostream>
#include <thread>

void work(int* x)
{
    for(int i=0; i<10000000; i++)
    {
        (*x)++;
    }
}

int main()
{
    int x = 0;
    std::thread t1(work, &x); // starts t1
    std::thread t2(work, &x); // starts t2

    t1.join(); // waits for t1 to end
    t2.join(); // waits for t2 to end
    std::cout << x << std::endl;
}
```
As expected, this outputs a number between 1e7 and 2e7. This is because L1/L2 caches for the two cores become stale when the other core's value gets updated. 

> **NOTE** Even if we pin a cpu(core) here, we still won't get 2e7 because the OS would schedule threads by time-slicing. Therein, we might have x loaded by t0, and before it is incremented, OS could schedule t1 and load a stale value.

On x86, `(*x)++;` roughly corresponds to
```x86
        mov     rax, QWORD PTR [rbp-24]
        mov     eax, DWORD PTR [rax]
        lea     edx, [rax+1]
        mov     rax, QWORD PTR [rbp-24]
        mov     DWORD PTR [rax], edx
```
which is clearly not atomic.

### Enter atomic

If we replace `int x` with `std::atomic<int> x`, we will indeed get 2e7. The time taken on my machine, however, increases from 0.09s to 1.26s. Our code is clearly not using the benefits of parallelism right now, but that is an algorithmic problem.

## Cache Coherence

```c++
void work(int* x)
{
    for(int i=0; i<10000000; i++)
    {
        (*x)++;
    }
}

struct my_pair
{
    std::atomic<int> x = 0;
    std::atomic<int> y = 0;
};

int main()
{
    my_pair p;

    std::cout << "distance = "
              << reinterpret_cast<char*>(&p.y)
               - reinterpret_cast<char*>(&p.x)
              << '\n';

    std::thread t1(work, &p.x);
    std::thread t2(work, &p.y);

    t1.join();
    t2.join();
    std::println("x: {}, y: {}",p.x, p.y );
}
```
Output:
```
distance = 4
x: 10000000, y: 10000000
./main  1.28s user 0.01s system 142% cpu 0.910 total
```

Note: 4 chars == 4 bytes. For ints, it would have been one byte.

```zsh
> sysctl hw.cachelinesize
hw.cachelinesize: 128
```

Therefore, if we change to
```c++
struct my_pair
{
    alignas(128) std::atomic<int> x = 0;
    alignas(128) std::atomic<int> y = 0;
};
```
we can get 
```
distance = 128
x: 10000000, y: 10000000
./main  0.25s user 0.01s system 64% cpu 0.401 total
```
which is clearly faster. std::atomic enforces atomicity, which is only possible by instructions that handle proper cache-coherence with [MESI](https://en.wikipedia.org/wiki/MESI_protocol)-like protocols.
But cache-invalidation is great for correctness, but can lead to [false-sharing](https://en.wikipedia.org/wiki/False_sharing) which we avoided by removing the shared-CacheLine of size 128 on our arm machine.

# Learning std::atomic

## What T can be std::atomic<T>?

trivially copyable types can be atomic. This is because the implementation cannot depend on arbitrary user-defined construction, destruction, copying, virtual dispatch, etc.

```
struct MyData
{
    int x;
    int y;
};

static_assert(std::is_trivially_copyable_v<MyData>);

std::atomic<MyData> data;
```

### Lock Free?

```c++
struct Pair
{
    std::uint64_t x;
    std::uint64_t y;
};

std::atomic<Pair> p;
```

The object is 16 bytes. Your CPU might not have a native 16-byte lock-free atomic RMW operation.
So `std::atomic<Pair>` may internally use a lock. 
We can check this via:
```c++
std::cout << std::atomic<Pair>::is_always_lock_free << '\n';
// or
std::cout << p.is_lock_free() << '\n'; // for a particular object
```

## std::atomic interface

For `std::atomic<int> x`, you can do
```c++
x++; // or fetch_add
x+=3; 
x|=2; // or fetch_or
x-=1; // or fetch_sub
x^=1; // or fetch_xor 
x=y;  // or x.store(y); etc..
T y = x; // T y = x.load() -- atomic read
```
but `x*=2` is not allowed.

No atomic multiply! This is a hardware level.  

`T z = x.exchange(y);` : Atomic(z=x; x=y;)

```
bool b = x.compare_exchange_strong(target, update); // CAS i.e. Compare and Swap
// if x == target, b = true and make x = update
// else, b = false and target = x.
// all this happens atomically

// in essence, `b` represents whether x was updated **by this thread**.
```

This is useful for updating things once in the form of while(!update_yet) :)
E.g., recall that multiplication is not atomic by default.

```c++
    // atomic<int> x;
    int x0 = x; // does not require x0 to be atomic. Think why?
    while(!x.compare_exchange_strong(x0, x0*2)){}
    // here, the target was trivially reachable and the while loop exits on first update.
```
Result: each thread multiplies x0 by 2. Notice that it makes sense for target to almost always start
with x itself. Update happens when "nobody else changed x since my last try".

### compare_exchange_weak

`x.compare_exchange_weak(x_old, x_new)` is same as its _strong_ counterpart except it can spuriously fail and return false, even when `x == x_old` (and x_old is not updated). 
This is because it might fail (~timeout) to get the exclusive access required to update x to x_new.

## Lock-free data structures

Atomic variables are used as an index into non-atomic data-structures.

## Memory order

Consider two threads t1, t2 running on core1 and core2 respectively. Core1 has some cache1 and core2 has cache2. The shared memory between them contains `int x, int y`.

When t1 executes an instruction that changes `x`, the change is first reflected in the relevant cache line in cache1. The cache-coherence protocol then ensures that other cached copies of that cache line are **invalidated** or **updated** as necessary.

Let's say t1 also updates y. This similarly involves the cache-coherence protocol for the cache line containing y. However, the coherence protocol primarily guarantees coherence for each individual memory location/cache line; it does not by itself specify the ordering in which another core must observe updates to different locations such as x and y.

The other, more famous source of reordering of instructions is compiler optimisations. 

The relative ordering with which -
1) another core can observe these updates 
2) the same core will execute these instructions  (can not be reordered for optimisation reasons)
is governed by the memory-consistency model. In C++, this is expressed through atomic operations and their memory_order semantics, which may be implemented using compiler constraints and, where necessary, hardware memory-ordering instructions (barriers/fences).

**relaxed**: no guarantees. 

**acquire**: all ops (both rw) scheduled after the barrier in the program become visible after the barrier-op. I.e. reads and writes cannot be reordered from after the barrier to before.

**release**: all ops (both rw) scheduled _before_ the barrier in the program become visible before the barrier.

**sequential consistency**: default. `std::memory_order_seq_cst` is both acquire + release.

E.g.
```c++
//initially
int x = 0;
std::atomic<int> y = 0; //atomic-index into non-atomic memory(x)

// t1
x = 42;
y.store(1, std::memory_order_release);


// t2
if (y.load(std::memory_order_acquire) == 1) {
    std::cout << x;
}
```

Guarantee: 
- t2 sees x=42 before y stores 1 (due to release semantics) => `std::cout << x` reads `x==42` since it loops until `y==1`.  
- t2's `std::cout<<x` is a read + print. It is guaranteed that the read will not be moved before the load of y. (due to acquire semantics)
